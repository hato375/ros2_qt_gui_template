# ROS 2 + Qt GUI アーキテクチャ・開発ガイド

## 1. 目的

本資料は、このプロジェクトへ機能を追加する際の前提、設計判断、および注意事項を定義します。

対象となる主な機能は次のとおりです。

- ロボット制御
- 画像処理と画像表示
- 3D点群処理と3D表示
- PLCおよび産業用機器との通信
- カメラキャリブレーション

環境構築とQt Creatorの設定については、`docs/development_setup_guide.md`を参照してください。
C++の記述規則については、`AGENTS.md`と`prompts/cpp_coding_rules.md`を参照してください。

## 2. 基本アーキテクチャ

アプリケーション内の処理を、次の3種類へ分離します。

```text
GUIスレッド
├─ Qtイベント処理
├─ ウィジェット更新
├─ 画像の最終表示
└─ VTK/OpenGLによる3D描画

ROS Executorスレッド
├─ Subscriberコールバック
├─ Serviceコールバック
├─ Action処理
├─ ROSタイマー
└─ ワーカーへの処理要求

ワーカースレッド
├─ OpenCV画像処理
├─ PCL点群処理
├─ Eigenによる計算
├─ キャリブレーション
└─ 時間のかかる通信・ファイル処理
```

現在のサンプルは、GUIスレッドとROS Executorスレッド、および重要イベントをGUIへ通知する経路を
実装しています。ワーカースレッドは、実際の処理内容とデータ型が決まった段階で追加します。

サンプルの`yds_interfaces/msg/EquipmentStatus`トピック監視は、Subscriberコールバックから
`yds::ros2::TopicReceptionMonitor`へ受信情報を渡します。共通モニターはROSメッセージ型に依存せず、
初回受信、受信時刻、受信件数、タイムアウト、および復旧の状態を管理します。camera、PLC、
Supervisorなどのノードでも、受信メッセージを表示用の`QString`へ変換して同じモニターを
利用できます。現在の`ros2_qt_gui`は、設定されたトピックごとにSubscriptionと共通モニターを1つずつ
所有し、Supervisorとして複数ノードの受信状態を一元監視します。タイムアウト時間はトピックごとに
設定し、更新周期の異なるcameraやPLCへ同じ値を強制しません。

設備の意味的な状態は、ROS API境界で`yds_interfaces::msg::EquipmentStatus`からQt Core型を使う
`yds::ros2::EquipmentStatus`へ変換します。通信状態と設備状態は別の型と通知経路で扱います。
これにより、`RECEIVING`かつ`ERROR`のような状態を失わずに表現できます。

共通パッケージ`yds_ros2`の`equipment_status_conversion.h`は、ROSメッセージとQt設備状態の
双方向変換を提供します。camera、PLC、Supervisorなどで変換を重複実装せず、このAPIを使用します。
ROSのゼロ時刻は無効な`QDateTime`へ変換し、受信時刻で補完するか未設定として扱うかは利用側が
決定します。

設備状態を送信するcamera、PLCなどのノードは、共通基底クラス
`yds::ros2::EquipmentStatusNode`を継承できます。派生ノードは`setEquipmentStatus()`で状態を更新し、
共通基底クラスが変更時の即時通知と最新状態の定期通知を行います。利用方法とパラメータは
`docs/equipment_status_node_guide.md`を参照してください。

新しい機能を実装するときは、GUI固有処理と複数ノードで再利用できる処理を確認します。ROS API境界の
型変換、状態管理、ログ用共通型などに汎用性がある場合は、依存関係を確認したうえで`yds_ros2`などの
共通パッケージへ配置します。

GUI通知は200ミリ秒周期のROSタイマーで集約し、高頻度入力時にQtのqueued connectionが無制限に
増えないようにします。GUI表示は最新データ優先であり、全メッセージの記録用途には使用しません。
状態遷移に応じたROSログ、アプリケーションイベント、および安全停止判断は共通モニターへ含めず、
利用するノード側の責務とします。

## 3. GUIスレッド

`QApplication::exec()`はメインスレッドで実行します。

次の操作はGUIスレッド以外から行わないでください。

- `QWidget`および派生クラスの生成、変更、破棄
- `QPixmap`を使用した画面更新
- VTKのRenderWindowおよびInteractor操作
- OpenGLコンテキストに依存する描画
- GUIタイマーの開始と停止

ROSまたはワーカースレッドからGUIを更新するときは、シグナル・スロットと
`Qt::QueuedConnection`を使用します。

```cpp
QObject::connect(
	&rosQtBridge,
	&RosQtBridge::heartbeatUpdated,
	&mainWindow,
	&MainWindow::setHeartbeatCount,
	Qt::QueuedConnection);
```

queued connectionで渡したデータは、受信側が実行するまで有効でなければなりません。
生ポインタや一時オブジェクトへの参照をスレッド間で渡さないでください。

## 4. ROS Executorスレッド

ROS 2 Executorは専用スレッドで`spin()`します。GUIスレッドから`spin()`を呼ぶと、
Qtイベントループへ制御が戻らず、GUIが応答しなくなります。

共通パッケージ`yds_ros2`の`yds::ros2::ExecutorRunner`は、次の責務を持ちます。

- `SingleThreadedExecutor`の生成
- ノードの登録
- Executorスレッドの開始
- `cancel()`による停止
- スレッドの`join()`
- 例外経路を含むRAIIによる後始末
- Executorスレッドの開始、停止、および例外のログ出力

`yds_ros2`の公開ヘッダーは`include/yds/ros2`、C++名前空間は`yds::ros2`とし、複数のROS 2
アプリケーションから再利用できる機能だけを配置します。

本プロジェクト群ではQtの利用を前提とするため、共通ライブラリでも`QString`、`QDateTime`などの
Qt Core型を基本データ型として使用できます。標準C++型との不要な相互変換は行わず、ROS APIが
標準C++型を要求する境界で必要な変換を行います。`QWidget`、`QPixmap`などGUIスレッドに依存する型は
共通ライブラリへ含めず、GUIパッケージ側で扱います。

ROSコールバックは短時間で終了させてください。コールバック内では、メッセージの検証、
必要なデータの保持、ワーカーへの要求までを行い、画像処理や点群処理を直接実行しないことを基本とします。

## 5. `SingleThreadedExecutor`の前提

現在は、コールバックの実行順序と共有状態を理解しやすくするため、
`SingleThreadedExecutor`を使用しています。

1つのコールバックが長時間動作すると、同じExecutor上の次の処理が待機します。

- 他のSubscriber
- Service応答
- Action処理
- ROSタイマー
- パラメータ変更

`MultiThreadedExecutor`への変更は、単純な性能改善ではありません。コールバックの同時実行、
Callback Group、共有状態の排他制御、および処理順序を設計する必要があります。変更する場合は、
対象処理、同時実行の必要性、排他方法を事前に明確にしてください。

## 6. 重い処理のワーカー

次の処理は、原則として専用ワーカーで実行します。

- OpenCVによるフィルタ、特徴抽出、推論前後処理
- PCLによるフィルタ、位置合わせ、セグメンテーション
- 大規模なEigen行列演算
- 画像、点群、設定ファイルの重い入出力
- 応答時間を保証できない外部ライブラリの処理

ワーカーを実装するときは、次の点を明確にします。

- 入力データの所有者
- 出力データの所有者
- 同時に処理できるタスク数
- キューの上限
- 停止要求の通知方法
- 処理中断の可否
- エラーの通知方法

ワーカースレッドからGUI部品を直接操作してはいけません。処理結果をqueued connectionで
GUIスレッドへ渡し、最終的な表示だけをGUIスレッドで行います。

## 7. 高頻度データとバックプレッシャー

カメラ画像や点群を無制限キューへ追加すると、処理速度が入力速度を下回ったときに、
遅延とメモリ使用量が増え続けます。

機能ごとに、次のいずれかの方針を選択してください。

### 最新データ優先

画像ビューワや3Dビューワなど、現在状態の表示に使用します。処理待ちの古いデータを破棄し、
最新データだけを保持します。

### 固定長キュー

多少の遅延を許容しつつ連続データを処理する場合に使用します。上限到達時に何を破棄するかを
明確にします。

### 全データ処理

検査結果や記録など、データ欠落を許容できない場合に使用します。この場合は、入力側の流量制御、
永続化、エラー時の復旧方法まで設計します。

データを破棄した場合は、必要に応じて件数や理由をログまたは診断情報として記録します。

## 8. スレッド間データ

スレッド間で共有するデータは、所有権と変更可能性を明確にしてください。

- 単純なカウンタやフラグには`std::atomic`を使用できる
- 複数の値を一貫して更新する場合はmutexで保護する
- 大きな画像や点群は不要なディープコピーを避ける
- 共有する読み取り専用データには`std::shared_ptr<const T>`を検討する
- 書き換え可能なオブジェクトを複数スレッドへ無制限に共有しない
- Qt queued connectionで独自型を渡す場合は、必要に応じてメタタイプ登録を行う

性能上の理由でコピーを省略する場合も、データの寿命と同時アクセスの安全性を優先します。

## 9. 終了処理

アプリケーションは、次のどちらからでも安全に終了できる必要があります。

- ユーザーがGUIを閉じる
- `ros2 launch`のCtrl+CなどでROS 2がshutdownされる

基本的な終了順序は次のとおりです。

1. 新規の処理要求を停止する
2. ROS Executorを`cancel()`する
3. ROS Executorスレッドを`join()`する
4. ワーカーへ停止を要求する
5. ワーカースレッドを`join()`する
6. ROS 2が有効な場合は`rclcpp::shutdown()`する
7. 所有オブジェクトを破棄する

実際の依存関係によって、ROS shutdownとワーカー停止の順序を調整する場合があります。
重要なのは、破棄済みオブジェクトへコールバックが到達しないことと、joinされていないスレッドを
残さないことです。

`cancel()`や`shutdown()`は、実行中の画像処理や点群処理を強制的に中断しません。長時間処理には
停止要求を定期的に確認する協調的キャンセルを実装してください。

## 10. 例外とエラー処理

- ライブラリ境界で発生する例外は適切な場所で捕捉する
- join可能な`std::thread`を残したまま例外を伝播させない
- デストラクタから例外を送出しない
- 空のcatchでエラーを無視しない
- GUIへ表示する内容とログへ記録する詳細情報を分ける
- 回復可能なエラーと、アプリケーションを停止すべきエラーを区別する

Qt GUIが必要なエラーダイアログは、`QApplication`が有効な間にGUIスレッドから表示します。

## 11. ログ

次のイベントをログへ記録します。

- ROSノード、カメラ、PLC、ロボットなどの接続と切断
- 初期化成功と初期化失敗
- エラーと復旧結果
- リトライ開始、回数、最終結果
- 設定変更
- 処理キューのオーバーフローやデータ破棄
- アプリケーションとワーカーの開始・停止

高頻度コールバックで毎回INFOログを出力しないでください。周期的な状態はDEBUGを使用するか、
一定時間ごとに集約します。

現在のサンプルでは、起動、設定、およびエラーなどの重要イベントを
`yds::ros2::ApplicationEvent`としてROS ExecutorスレッドからGUIへ通知できます。この共通型は
`yds_ros2`の公開APIです。通知には`RosQtBridge`のqueued connectionを使用し、GUIのイベント表示は
最新500件に制限します。ROSログは診断用の詳細情報、GUIログは運用者が確認する重要情報として
役割を分けます。

GUIへ通知するイベントの重要度は次のように使い分けます。

- `kInfo`: 接続、切断、起動、停止、設定変更
- `kWarning`: リトライ、一時的な異常、性能低下
- `kError`: 処理は失敗したが、継続または復旧が可能なエラー
- `kCritical`: 安全な継続が困難で、設備またはアプリケーションの停止判断が必要なエラー

`kCritical`の通知自体には停止処理を持たせず、安全停止は呼び出し側で明示的に実行します。
デバッグ情報や高頻度な内部状態はGUIイベントへ追加せず、ROSのDEBUGログを使用します。

## 12. GUI表示用データ

画像処理用データとGUI表示用データを区別します。

- OpenCVの`cv::Mat`は処理データとして扱う
- Qt表示用への変換は所有権とデータ寿命を明確にする
- `QImage`が外部バッファを参照する場合、表示完了までバッファを保持する
- `QPixmap`はGUIスレッドで生成・使用する
- 点群処理結果とVTK表示オブジェクトを直接共有しない
- VTK表示用データへの変換とRenderはGUI側の責務として分離する

表示レートと処理レートは同一である必要はありません。高頻度入力に対しては表示を間引き、
GUI応答性を維持します。

## 13. 依存ライブラリ

依存ライブラリを追加するときは、次の点を確認します。

- Ubuntu 22.04とROS 2 Humbleで利用可能か
- WindowsとLinuxの両方で使用できるか
- ライセンス上の問題がないか
- バージョン競合がないか
- 配布先でランタイムを用意できるか
- CMakeとpackage.xmlの両方へ適切に依存関係を追加したか

現時点ではQt 5を使用します。Qt 6への変更や、Qt 5とQt 6の混在は行わないでください。

## 14. 実装前の確認事項

新しい機能を実装する前に、少なくとも次を確認します。

- どのスレッドで実行するか
- 入力データと出力データの所有者は誰か
- GUIへ通知する方法
- 処理時間の上限
- キューの上限と破棄方針
- 停止中に処理が残っている場合の扱い
- エラー時に継続、リトライ、停止のどれを選ぶか
- 必要なログ
- WindowsとLinuxでの差異

## 15. 検証

変更内容に応じて、次を確認します。

- C++17でビルドできる
- コンパイラ警告が増えていない
- Qt GUIが応答し続ける
- ROSメッセージがない状態でも正常に動作する
- 高頻度メッセージでメモリが増え続けない
- 重い処理中もGUIとROS通信が停止しない
- GUIを閉じたときに正常終了する
- Ctrl+Cで正常終了する
- エラー経路でも全スレッドがjoinされる
- 接続、切断、エラー、設定変更がログへ出力される

検証できなかった項目がある場合は、完了報告で明示してください。
