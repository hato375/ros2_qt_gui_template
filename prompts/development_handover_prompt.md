# 開発セッション引き継ぎ資料作成プロンプト

## 目的

長くなったAI開発セッションを終了し、新しいセッションで安全かつ短時間に作業を再開するための
`docs/development_handover.md`を作成・更新するプロンプトです。

このプロンプトは、会話の要約だけに依存せず、リポジトリ、Git、テスト、CIの実状態を確認してから
引き継ぎ資料を作ることを重視します。セッション終了時に、以下の「実行用プロンプト」をそのまま
AIエージェントへ渡してください。

## 実行用プロンプト

```text
この開発セッションを終了し、次のセッションへ移るための引き継ぎ資料を作成してください。

対象リポジトリのルートにあるAGENTS.mdと、既存のdocs/development_handover.mdを最初から最後まで
読んでください。AGENTS.mdの指示を最優先し、既存の引き継ぎ書は形式と履歴を理解するために使用して
ください。ただし、既存記述や会話中の記憶を現在の事実としてそのまま転記しないでください。

次の調査を行い、実際の結果を根拠としてください。ソース、設定、Git履歴、外部サービスの状態は
変更しないでください。

1. 現在日時、作業ディレクトリ、現在のブランチ
2. git status --short --branch
3. git log -10 --oneline --decorate
4. remote名と接続先リポジトリ、および現在ブランチのupstreamとahead/behind
   - remote URLに認証情報が含まれていないことを確認してから扱う
   - 認証情報を含むURLは、コマンド出力を含めて表示・転記しない
5. HEAD以降または作業中の変更内容
   - ステージ済み、未ステージ、未追跡を区別する
   - ユーザーの変更をAI自身の変更と決めつけない
6. このセッションで完了した作業と、それを裏付けるコミットまたは差分
   - 既存の引き継ぎ書に基準コミットがあれば、そのコミット以降を確認する
   - セッション境界や作業者を確認できない変更は、今回の作業と断定しない
7. 実行したビルド、テスト、静的検査と、その正確な結果
8. 直近CIの対象コミット、状態、URL
   - 利用可能な認証済み連携または公開APIで確認する
   - 確認できない場合は、最後に確認できた結果と確認不能の理由を分けて書く
9. 関連する設計資料、バックログ、Issue、Pull Request
10. 作業中に決定した設計方針、採用理由、見送った案

このセッションですでに実行したビルドやテストの結果を、ログなどで確認できる範囲で記録してください。
この引き継ぎ依頼だけを根拠に新しいビルドやテストを実行しないでください。必要な検証が残っている場合は、
未実施理由と推奨コマンドを記録してください。進行中の開発依頼ですでに検証実行まで許可されている場合に
限り、その範囲内の非破壊的な検証を継続できます。

この依頼だけを根拠に、引き継ぎ書以外のコードや資料の修正、コミット、push、CI再実行、Issue作成などの
状態変更は行わないでください。引き継ぎ書以外に修正が必要だと分かった場合は、残件として記録して
ください。

調査後、docs/development_handover.mdを次の構成で更新してください。該当事項がない節も省略せず、
「なし」または「未確認」と明記してください。

# 開発引き継ぎ書

- 更新日時（タイムゾーン付き）
- 対象リポジトリ

## 1. 30秒で分かる現在地

- 今回達成したこと
- 現在のブランチとHEAD
- originとの同期状態
- 引き継ぎ書更新前の作業ツリーの状態
- 引き継ぎ書更新後の最終作業ツリーの状態
- 直近の検証結果
- 直近CIの状態とリンク
- 次に行う推奨作業を1件

## 2. 完了した作業

- 目的、変更内容、主要ファイルを機能単位で記述する
- 関連コミットのハッシュと件名を記述する
- 単なるファイル一覧ではなく、何ができるようになったかを説明する

## 3. 現在進行中の作業

- 未コミット変更を、ステージ済み・未ステージ・未追跡に分ける
- 各変更の目的、現状、残り作業を記述する
- 中断地点を、次の担当者が最初の操作を判断できる粒度で記述する
- 引き継ぎ書更新前に存在した変更と、今回更新した引き継ぎ書を区別する
- 作業ツリーがクリーンなら、そのことを明記する

## 4. 設計判断と制約

- 重要な「何を」「なぜ」を記述する
- 見送った案と見送り理由を、今後の再検討に必要な範囲で記述する
- 安全性、互換性、公開インターフェース、運用上の制約を記述する
- コードや既存設計資料から確認できる事実と、推測を区別する

## 5. 検証結果

- 実行コマンド、実行日時、成功・失敗・スキップ数を可能な限り記述する
- 未実施の検証と、その理由を明記する
- 失敗した試行は、症状、原因、既に試した対処を記述する
- 「テスト成功」とだけ書かず、対象範囲が分かるようにする

## 6. GitとCI

- ブランチ、HEAD、upstream、ahead/behind
- 引き継ぎ書更新前と更新後の作業ツリーの状態
- 未pushコミットの有無
- 直近CIのworkflow名、run番号、対象コミット、結果、URL
- CI未確認の場合は、その理由と次回の確認方法

## 7. 残件と次の作業候補

- 優先度順に並べる
- 各項目に目的、最初の具体的な一手、完了条件を付ける
- 「必須」「推奨」「低優先度」を区別する
- 次の推奨作業は1件に絞り、選定理由を書く

## 8. 再開手順

- 新セッションで最初に読むファイルを順番付きで列挙する
- 状態確認コマンドをコピー可能なコードブロックで示す
- ビルド・テストの標準コマンドを示す
- 最初に着手するファイルまたは機能を示す
- 引き継ぎ書の情報を鵜呑みにせず、GitとCIを再確認するよう明記する

## 9. 関連資料

- 関連文書をリポジトリ相対パスで示し、各資料の役割を1行で説明する
- 外部Issue、Pull Request、CIなどは恒久的なURLを付ける

記述時は次の品質基準を守ってください。

- 日本語で、短くても情報密度の高い文章にする
- 「完了」「進行中」「未確認」「推測」を混同しない
- 日時、コミット、ブランチ、件数など、変化しやすい情報には具体値を使う
- コマンド出力を大量に貼らず、判断に必要な値を要約する
- 秘密情報、認証情報、個人情報、顧客固有情報を記録しない
- ローカルの絶対パスは、再開に不可欠な場合を除いてリポジトリ相対パスにする
- 既存の正本がある情報は重複させず、正本への参照と今回必要な要約だけを書く
- 実在しないファイル、テスト結果、CI結果、コミットを推測で作らない
- セッション境界または作業者が不明な変更を、このセッションの成果として推測しない
- 将来変わる可能性がある記述には「更新日時点」と付ける

ファイル更新後、次を確認してください。

- git diff --check
- 引き継ぎ書更新後にgit statusとgit logを再実行すること
- 更新前のスナップショットと更新後の最終状態を混同していないこと
- 引き継ぎ書に記載した最終Git情報と、再実行したgit status/logが一致すること
- 記載したファイルパスが存在すること
- 記載したコミットがgit logで参照できること
- 未確認事項が、確認済みの事実のように書かれていないこと

最後に、変更したファイル、確認したGit状態、実施した検証、残る未確認事項を報告してください。
コミットは、変更内容と検証結果を提示して私の確認を得るまで行わないでください。
```

## 新しいセッションを開始するときの短い依頼例

作成済みの引き継ぎ書を利用して再開するときは、次のように依頼します。

```text
このリポジトリの開発を再開します。AGENTS.mdとdocs/development_handover.mdを最初から最後まで読み、
Gitの現在状態と直近CIを実際に確認してください。引き継ぎ書との差分、現在のリスク、次に行う推奨作業を
報告してください。私が作業を選ぶまでは、ファイル変更、コミット、pushを行わないでください。
```

## 設計上の狙い

- `AGENTS.md`には長期間変わりにくい規約を置き、引き継ぎ書にはセッションごとに変わる状態を置きます。
- Git、テスト、CIを再確認させることで、古い引き継ぎ書や会話要約による誤認を防ぎます。
- 完了、進行中、未確認を分離し、次の担当者が残作業を誤って完了扱いしないようにします。
- 設計理由と見送った案を残し、コードだけからは復元しにくい判断の背景を保持します。
- 次の作業に「最初の一手」と「完了条件」を付け、再開直後の探索時間を減らします。
- 引き継ぎ書の更新だけを許可し、それ以外の状態変更を禁止することで、セッション終了時の意図しない
  修正やpushを防ぎます。
